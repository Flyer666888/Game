# 《逆鳞》UE5.8 开发方案：AI 编程协作与编辑器对接

版本：v0.1  
日期：2026-10-01  
项目阶段：开发规划与 AI 交接规范  
目标平台：Windows PC VR，双手柄  
开发引擎：Unreal Engine 5.8；具体补丁号在 M0 锁定  
流程目标：单人、三关、首次成功通关约 20–30 分钟

本方案承接 GDD v0.1 和 [VR 关键画面示意](./VR_关键画面示意.md)。文中的角色、装备、数值与节点移动方式，沿用现阶段的原型建议；PC VR、双手柄、三关时长和 UE5.8 已由用户确认。

“对接 AI”在本文中指：让 AI 编程助手编写、编译和验证源码，并通过 UE5.8 官方 Unreal MCP 操作编辑器。普通敌人的游戏 AI 由确定性的战斗状态与调度规则实现。具体 AI 客户端尚未指定。

## 1. 实施目标与交付范围

### 1.1 最终交付

1. 能在指定头显及 OpenXR Runtime 上启动的 Windows 游戏构建。
2. 三关完整救援流程：群体割草、守点解救、弹幕 Boss。
3. 左右手切换、站立／坐姿、暂停与追踪丢失处理。
4. 主手挥砍与刃气，副手格挡、精准反弹、范围震荡及爆发技能。
5. 波次与攻击调度、两次主要装备成长、检查点重试。
6. 实机性能报告、关卡完成记录、关键规则测试报告。
7. 可供 AI 接续的源代码、数据资产清单、任务状态与配置记录。

### 1.2 原型内容预算

| 内容 | 首版数量／范围 |
|---|---|
| 玩家角色 | 1 个妖族龙子角色，以双手和前臂表现为主 |
| 主装备 | 逆鳞刃＋护心镜，外观暂定 |
| 普通／精英敌人 | 持剑弟子、御符弟子、护阵执事、破阵修士 |
| Boss | 1 个宗主，3 阶段，共用攻击语言 |
| 关卡 | 3 个主地图，另有开发测试地图 |
| 成长 | 2 次主要装备升级；首版固定路线 |
| 叙事 | 开场、挚友解救、宗主阻拦、结尾 |
| AI 编辑器连接 | 1 个 AI 客户端对应 1 个正在打开的 UE 项目 |

先用灰盒角色、简单装备和低成本特效完成玩法，再替换为与画面示意一致的正式资产。

### 1.3 完成的判断

“源码已生成”“成功编译”“编辑器能运行”“头显能玩”“三关可交付”分别记录，不能互相代替。

项目完成以三关打包版、指定设备实测与验收报告为准。当前文档与接口名称用于实施指导；工程初始化和实际连接验证由 M0 完成。

## 3. 技术路线

### 3.1 引擎与插件

| 项目 | 用途 | 策略 |
|---|---|---|
| UE5.8 C++ 项目 | 核心规则与可审阅源码 | 锁定补丁号，不在里程碑中途自动升级 |
| VR Template | 验证 OpenXR、基础追踪和交互 | 保留模板作为参考；游戏 Pawn 逐步使用项目类 |
| OpenXR | 头显／手柄适配 | 为目标 Runtime 配置并实测 |
| Enhanced Input | 战斗、菜单、调试输入 | 使用语义动作和映射上下文 |
| Niagara | 刀光、灵气、符阵和弹丸视觉 | 视觉与伤害判定分开 |
| UMG／Widget Component | 世界内 UI、设置、调试 | 尽量事件驱动更新 |
| Navigation System | 敌人场地移动 | 固定战斗区域，烘焙 NavMesh |
| Unreal MCP＋All Toolsets | AI 操作编辑器 | 优先采用官方能力 |
| Python Editor Script Plugin | 导入与批量资产生产 | 按需要启用，仅承担编辑器自动化 |
| Automation／Functional Testing | 规则与场景测试 | 建立针对关键故障的测试 |

Epic 的 VR Template 使用 OpenXR，可作为设备接入的起点；模板文档包含历史输入描述，实际输入资产以安装的 5.8 工程为准。[VR Template 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/vr-template-in-unreal-engine)

Enhanced Input 提供 Input Action 与 Mapping Context，适合隔离战斗、菜单和设备绑定。[Enhanced Input 官方说明](https://dev.epicgames.com/documentation/unreal-engine/enhanced-input-in-unreal-engine)

### 3.2 代码与蓝图分工

| 层 | 主要内容 | 交付方式 |
|---|---|---|
| C++ 规则层 | 命中、护势、精准格挡、调度、存档、Boss 状态 | 可编译源码与测试 |
| 蓝图表现层 | 模型、动画、声音、特效、场景实例与事件响应 | 薄蓝图、明确父类和资产路径 |
| 数据层 | 敌人、攻击、波次、成长、关卡节点、Boss 技能 | Data Asset 与配置清单 |
| 编辑器自动化 | 灰盒摆放、批量配置、验证、截图和报告 | MCP；缺口由项目编辑器工具补充 |
| 人工实机验证 | 舒适度、真实挥砍、可读性、设备兼容、手臂疲劳 | 录屏、测试表、Profiler 数据 |

关键战斗规则集中在 C++，蓝图订阅结果并表达反馈。避免在各蓝图中分别计算伤害，造成同一弹丸结算多次。

### 3.3 渲染基线

推荐原型起点：

- Forward Shading。
- MSAA，从 2x／4x 对比测试。
- Instanced Stereo，在目标 RHI 与设备上验证。
- 静态／预计算照明为主，少量必要动态光。
- 克制使用透明屏障、粒子叠加、动态阴影。
- 运动模糊、镜头摇晃和强制景深关闭。
- 先用传统 LOD 和明确的预算完成内容。

Forward 与 MSAA 作为起点需要在实际场景测量，不能据此承诺固定性能提升。[Forward Shading 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/forward-shading-renderer-in-unreal-engine)

Instanced Stereo 的开关与支持条件以设备测试记录为准。[XR Performance Features 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/xr-performance-features-in-unreal-engine)

Nanite、Lumen 等高级特性采用单独试验分支评估，不与以上基线默认混用。形成对照报告后才调整全项目渲染路线。

## 4. AI 对接：源码通道与编辑器通道

### 4.1 工作流

~~~mermaid
flowchart LR
    A[人类策划与技术负责人] --> B[需求文档与任务卡]
    B --> C[AI 编程助手]
    C --> D[C++ 源码与配置修改]
    D --> E[UBT 编译与测试]
    C --> F[官方 Unreal MCP]
    F --> G[UE5.8 编辑器]
    G --> H[资产配置与测试地图]
    H --> E
    E --> I[日志 截图 测试报告]
    I --> C
    I --> J[头显实机验收]
    J --> A
~~~

源码通道负责文本文件、构建和静态检查；编辑器通道负责 UE 资产与场景操作。两个通道都回到同一任务的验收证据。

### 4.2 官方 MCP 接入步骤

UE5.8 官方 Unreal MCP 目前是实验功能。启用 Unreal MCP 与 All Toolsets 后，可连接默认本地 HTTP 地址。实际工具由编辑器发现；项目对同一编辑器串行执行调用。[Unreal MCP 官方说明](https://dev.epicgames.com/documentation/unreal-engine/unreal-mcp-in-unreal-editor)

实施步骤：

1. 在项目内启用 Unreal MCP、All Toolsets，完成依赖启用和编辑器重启。
2. 在 Editor Preferences 中配置 MCP；默认地址为 `http://127.0.0.1:8000/mcp`。
3. 按选定客户端生成配置，使用官方控制台命令模板：
   ~~~text
   ModelContextProtocol.StartServer
   ModelContextProtocol.GenerateClientConfig <Client>
   ~~~
   `<Client>` 替换为官方文档支持且实际使用的客户端标识。
4. 从项目根目录启动客户端，核对生成配置的位置和连接日志。
5. 先读取当前地图与选中 Actor，再进行一个可回滚的灰盒创建测试。
6. 工具搜索模式下，按 `list_toolsets → describe_toolset → call_tool` 发现能力，保存真实 schema。
7. 导出当前工具清单和一次测试记录，作为后续 AI 任务的上下文。

不要仅依据端口能连接就认为 MCP 可用；验收需要真实完成“读取 → 创建测试对象 → 读回属性 → 清理测试对象”闭环。

### 4.3 能力清单

M0 输出 `Docs/AI/Capabilities.md`：

| 能力 | 状态值 | 需要的证据 |
|---|---|---|
| 读取地图／Actor／属性 | 可用／不可用／未验证 | 工具名、schema 和调用结果 |
| 创建 Actor 与编辑属性 | 同上 | 测试对象及属性读回 |
| 创建材质或数据资产 | 同上 | 保存后重新加载 |
| 创建蓝图子类 | 同上 | 父类、编译结果、保存结果 |
| 修改蓝图图表 | 同上 | 实际工具支持范围，不预先假定 |
| 启动测试／获取日志 | 同上 | 报告路径与失败返回 |
| 截图／PIE 控制 | 同上 | 命令、输出和退出行为 |
| 自定义 Toolset | 同上 | 本机类定义和工具发现结果 |

具体工具名称在能力发现后填入任务。本文后面出现的项目工具名称都是拟开发接口。

### 4.4 日常执行约束

- 对同一编辑器的资产写入顺序执行。
- 修改前核对地图与资产路径，修改后读回关键属性。
- 保存变化的资产，记录内容目录和新增对象。
- 遇到超时，先检查编辑器结果再重试；避免重复生成对象。
- 反射声明变更后安排完整编译和编辑器重启。
- 代码、工具 schema 与内容记录保持同一提交状态。
- 开发连接保留在本机回环地址；发布构建验证不启动 MCP 服务。

MCP 的可执行能力必须以本机清单为依据；本方案为不依赖它的核心运行时代码保留正常编译与游戏验证路径。

### 4.5 官方工具有缺口时

先记录缺口，使用 UE 编辑器已有工具完成一轮任务；若缺口反复出现，再实现一个窄范围项目 Toolset。

项目 Toolset 采用 `UToolsetDefinition` 与静态、可反射的工具方法。具体声明和 include 由 AI 对照本机 5.8 头文件验证。[UToolsetDefinition API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/ToolsetRegistry/UToolsetDefinition)

Python 可用于资产导入和布局脚本；运行时战斗仍由 C++／蓝图执行。[Unreal Editor Python 官方说明](https://dev.epicgames.com/documentation/unreal-engine/scripting-the-unreal-editor-using-python)

### 5.2 版本管理

- 源码、Config、项目文件、Content 及其关联文件进入版本管理。
- 按 UE 项目规则忽略 Intermediate、DerivedDataCache、可重建的 Binaries 和本地构建产物。
- 大型二进制资产按团队现有 Git LFS／Perforce 流程管理。
- 每项任务形成一组可独立回滚的源码、配置和内容变化。
- 新增蓝图子类、属性变更、资产迁移要记录影响路径。
- 不直接改写 `.uasset`／`.umap` 二进制内容；通过编辑器生产并保存。

### 6.1 事件流

~~~mermaid
sequenceDiagram
    participant P as 玩家装备
    participant R as 战斗结算器
    participant G as 防御组件
    participant T as 受击目标
    participant F as 反馈路由
    P->>R: 提交接触候选与攻击实例
    R->>G: 若命中屏障，查询防御结果
    G-->>R: 普通格挡 精准格挡 破防 未拦截
    R->>T: 结算有效伤害或反弹所有权
    R->>F: 发布一次 CombatResult
    F-->>P: 音效 震动 特效
~~~

反弹改变弹丸状态和阵营，使用同一结算入口。反馈不再反向触发伤害。

## 7. 数据契约与共同规则

### 7.1 内容配置类型

| 数据 | 必要字段 |
|---|---|
| EnemyDefinition | StableId、生命、移动速度、Prefab／Class、攻击配置、灵气奖励 |
| AttackDefinition | StableId、伤害、预警、攻击窗、冷却、可格挡／可反弹／可打断标识 |
| ProjectileDefinition | 速度、半径、寿命、阵营、碰撞策略、反馈资产 |
| WaveDefinition | Seed、阵容池、生成位置、组间隔、场上上限、攻击预算 |
| CombatNodeDefinition | NodeId、位置引用、EncounterId、进入／完成条件、下一节点 |
| LevelDefinition | LevelId、节点序列、目标、检查点与预加载资源 |
| BossPatternDefinition | 阶段、弹组、节拍、阵眼、输出窗口、终止条件 |
| UpgradeDefinition | UpgradeId、触发条件、效果、保底奖励 |
| ComfortDefinition | 移动模式、遮罩、转向角度、坐姿与动作辅助参数 |

主配置使用 Data Asset；需要统一查找、加载和打包的配置使用 Primary Data Asset。M0／M3 验证 Asset Manager 扫描和 Cook 包含关系。

### 7.2 单位

- 世界距离：UE 厘米，100 cm = 1 m。
- 速度：cm/s。
- 时长：秒。
- 角度：度。
- 生命与护势：无单位数值。
- 日志与存档字段必须带含义明确的单位后缀，例如 `SpeedCmPerSec`。

不允许同一字段在不同模块中分别按米和厘米解释。

### 7.3 战斗结果

建议定义以下项目契约；字段最终与本机 C++ 反射约束适配：

~~~text
CombatContact
  AttackInstanceId
  SourceRuntimeId
  TargetRuntimeId
  ProjectileGeneration
  ContactTime
  HitPosition
  HitNormal
  IncomingVelocity
  AttackDefinitionId

CombatResult
  ResultId
  AttackInstanceId
  Outcome: Hit | Blocked | PerfectParry | GuardBroken | Ignored
  AppliedDamage
  GuardSpent
  NewProjectileFaction
  FeedbackTag
~~~

约束：

1. 每次独立挥砍／发射分配一个攻击实例 ID。
2. 对象池复用使用 generation，防止上一轮身份继续生效。
3. 一次挥砍对同一目标只结算一次。
4. 一枚被拦截的弹丸不能同一帧再伤害屏障后的玩家。
5. 玩家和法阵是不同受击目标，但使用相同结算契约。
6. 结算结果必须可追踪到来源和目标，便于排查误伤。

### 7.4 游戏时间与暂停

战斗倒计时、冷却、精准窗口、波次、Boss 技能和解救进度统一服从暂停状态。

追踪与暂停菜单继续正常工作。模块不能各自用不同的时间尺度计算战斗窗口；恢复后的首帧重置刀刃历史采样，避免姿态跳变产生攻击。

### 7.5 碰撞配置

在项目配置中建立明确的 Object／Trace Channel 和 Collision Profile，字段与响应矩阵在 ENV-02 登记。

| 配置对象 | 应参与的检测 | 不承担的功能 |
|---|---|---|
| PlayerBody | 敌方弹丸、有效近战、场景边界 | 不与自身装备结算伤害 |
| EnemyBody | 玩家刀刃、玩家刃气、反弹弹丸 | 不与同阵营普通弹丸结算伤害 |
| GuardSurface | 当前有效的来袭攻击轨迹 | 不直接扣除目标生命 |
| RitualBody | 明确指向法阵的敌方攻击 | 不混用玩家伤害保护计时 |
| BossSeal | 玩家刃气与规定的攻击 | 不受装饰粒子碰撞影响 |
| WorldObstacle | 弹丸路径与必要场景阻挡 | 不形成额外伤害事件 |

刀刃 Trace 与弹丸 Sweep 使用指定查询通道，统一选取有效接触。屏障失效、反弹与阵营切换需要同步响应和忽略集合。实体检测与反馈动画不共享隐式碰撞规则。

## 8. VR Pawn、输入与自动推进

### 8.1 Pawn 层级

自动移动作用于根节点。Camera 和 MotionController 保留追踪驱动的局部姿态，不通过脚本直接重写相机俯仰或翻滚。

身体代理根据相机位置计算躯干范围，支持坐姿和身高差异。头显碰墙采用软提示／遮挡处理，不能把虚拟头部强行推离真实追踪姿态。

### 8.2 语义输入

| Input Action | 行为 | 初始绑定 |
|---|---|---|
| IA_BladeQi | 刃气发射 | 主手扳机 |
| IA_Guard | 屏障举起／收起 | 副手扳机 |

| IA_Burst | 逆鳞爆发 | 主手主功能键 |

挥砍由追踪轨迹识别，不映射为一个普通按键。左右手交换改变“主手／副手”语义绑定，并同步装备、UI 与震动目标。

Mapping Context：

- `IMC_Combat`：战斗动作。
- `IMC_Menu`：菜单交互。
- `IMC_Debug`：仅开发构建的测试动作。

进入暂停菜单时，屏蔽战斗输入并取消未完成的发射／举盾状态；恢复后按当前输入重新进入正常状态。

### 8.3 路线状态

~~~text
Idle → MovementCue → Transitioning → NodeArrived
     → CombatReady → CombatActive → NodeCompleted
     → Reward → MovementCue
~~~

其他状态：Paused、TrackingLost、Failed、Restoring。

节点完成条件使用“目标已完成＋有效威胁已处理”，不能仅凭计时器移动玩家离开尚在攻击的敌人。

默认舒适模式使用淡出转移；连续推进作为可选模式。转场结束重置历史武器轨迹、未消费攻击候选和近身碰撞缓存。

### 8.4 验收

- 真实头手追踪正常，左右手切换正确。
- 自动转场不制造一次虚假挥砍。
- 暂停和追踪丢失期间没有伤害。
- 恢复时有准备提示，敌人不立即无预警攻击。
- 镜头无自动摇晃、翻滚或强制朝向。
- 坐姿可完成核心动作。

## 9. 近战实现

### 9.1 首版碰撞策略

采用刀刃多点轨迹扫掠：

1. 在刀根、中段和刀尖设置采样点。
2. 每帧读取游戏线程上的姿态，保留上一帧样本。
3. 用球体扫掠覆盖各点移动路径，并检查刀刃当前覆盖。
4. 速度与挥砍有效性依据追踪空间的手部运动判断。
5. 命中候选交由战斗结算器去重。

关键点：根节点的自动移动不能计入“玩家主动挥刀速度”。

不要仅用普通 overlap 事件识别挥砍；快速动作可能漏判，静止接触又可能重复触发。

### 9.2 挥砍状态

~~~text
Ready → SwingActive → Recovery → Ready
~~~

- 进入有效挥砍时创建 AttackInstanceId。
- 同一次挥砍维护已命中目标集合。
- 允许一刀命中多个不同敌人。
- 低速抖动、静止抵住、恢复阶段不刷伤害。
- 追踪跳变、暂停恢复、转场时清空历史样本。
- 采样跨度异常时记录诊断，不直接制造超长攻击路径。

首版普通弟子生命 30、有效近战伤害 30，先验证“一刀一杂兵”。挥砍阈值不写死为最终数值，提供开发调参面板与轻动作辅助选项。

### 9.3 测试

- 正常挥砍、快速挥砍、轻动作分别测试。
- 同一次挥砍接触同一目标多次，只扣一次生命。
- 一次横扫可以击败两个近距离杂兵。
- 静止刀刃贴住敌人不连续伤害。
- 节点转移、分段转向和追踪恢复不产生误伤。

## 10. 弹丸、格挡与精准反弹

### 10.1 弹丸

基础弹丸由 C++ Actor／组件驱动，配置速度、半径、寿命与阵营。原型从直线弹丸开始；装饰弹幕使用 Niagara。

高速弹丸每帧执行路径扫掠，使用实际移动路径选择最先接触的有效几何体。屏障、身体与环境冲突由单一结算器处理。

池化对象在返还时重置：

- 生命周期和计时器。
- 阵营、来源、攻击 ID 与 generation。
- 目标引用、碰撞忽略集合。
- 特效与声音句柄。
- 运动状态与反弹次数。

先验证低数量行为正确，再加入对象池，避免把规则问题和复用问题混在一起。

### 10.2 屏障

屏障采用可与弹丸轨迹相交的简单几何体，保留方向与有限覆盖。视觉网格与逻辑碰撞体分开配置。

防御顺序：

1. 判断攻击类别是否可被当前防御手段拦截。
2. 判断屏障状态、朝向和碰撞交点。
3. 判断是否进入精准窗口。
4. 结算护势／反弹／普通格挡。
5. 发布一次反馈结果。

破防后屏障视觉与逻辑状态同步。无法拦截时，继续处理弹丸剩余路径，不能把弹丸消失误当作防御成功。

### 10.3 精准窗口

初始窗口约 0.18 秒，以战斗时间计算。

建议再举盾条件：

- 输入先回到收盾状态并保持短时间。
- 两次窗口有最小间隔。
- 重新举盾产生明确窗口。
- 持续按住和扳机阈值附近抖动不会反复重开窗口。

窗口、再武装时间和输入阈值可调。主手刀的近战招架与副手弹丸反弹使用统一结果类别，但具有各自的有效攻击类型。

### 10.4 反弹行为

精准反弹：

- 切换弹丸阵营与伤害来源。
- 清理对原目标的伤害候选。
- 向可见、合法反击目标修正方向；没有目标则按反射方向飞离。
- 经过短暂源屏障忽略后恢复正常碰撞。
- Boss 飞剑优先指向规定的护阵目标。
- 限制反弹次数与寿命，避免永久来回反弹。

“成功反弹”由轨迹、声音、震动和 Boss 护阵变化共同确认。

### 10.5 护势、技能与初始参数

| 项目 | 原型起点 |
|---|---:|
| 玩家生命／护势 | 各 100 |
| 刃气伤害／间隔 | 15／0.35 秒 |
| 普通弹丸格挡消耗 | 12 护势 |
| 普通近战格挡消耗 | 20 护势 |
| 屏障维持消耗 | 6／秒 |
| 收盾恢复延迟／恢复速度 | 0.8 秒／25 每秒 |
| 破防时长 | 1.2 秒 |
| 范围震荡冷却／半径 | 8 秒／250 cm |
| 玩家连续受伤保护 | 约 0.65 秒 |

这些数值沿用 GDD 的调试起点，必须与攻击节奏一起调整。

爆发能量由击杀、有效进攻和精准格挡获取；常规防御不能依赖大招是否就绪。能力组件向结算器发出清场／击退请求，再由反馈路由播放表现。

## 11. 敌人 AI 与攻击调度

### 11.1 状态机

~~~text
Spawn → Approach → WaitForSlot → Telegraph
      → Attack → Recover → Approach
~~~

其他状态：Staggered、Dead、Despawn、Paused。

原型使用可读的小型状态机；若团队已有 Behavior Tree／StateTree 标准，可在保持接口和测试不变的前提下替换内部实现。

敌人动画 Notify 提交“攻击窗口开始／结束”，伤害仍由统一结算器处理。Notify 不直接反复扣血。

### 11.2 四类敌人

| 类型 | 主要逻辑 | 特殊条件 |
|---|---|---|
| 持剑弟子 | 接近、申请名额、预警挥砍 | 一次有效近战可击败 |
| 御符弟子 | 保持距离、站位、发射符弹 | 法阵目标需单独预警 |
| 护阵执事 | 防御、重击、失衡反击窗口 | 不能只靠额外生命区分 |
| 破阵修士 | 移动至施法位、干扰法阵 | 明确高优先级轮廓与提示 |

导航失败应释放攻击名额并改位；敌人不能因走不到目标而让波次永久卡住。

### 11.3 Attack Director

初始攻击预算示例：

- 近战名额：2。
- 远程名额：1。
- 高威胁施法名额：1，与部分普通攻击组合互斥。
- 同时活跃战斗敌人：先以 12 为测试起点。

名额并不表示可以同一瞬间全部造成伤害。调度器同时管理攻击准备与预计命中时间，错开不合理组合。

请求包含：敌人 ID、攻击 ID、目标 ID、方向、预计预警和命中时间、威胁权重。

必须在死亡、受击打断、失去目标、暂停／重试清理和关卡结束时释放名额。名额有超时保护和诊断信息。

### 11.4 公平性

- 刷新后先展示，再允许攻击。
- 玩家身后不生成无预警高威胁攻击。
- 同一时段不得安排超出双手可处理范围的强制应对。
- 守点的高威胁目标有数量上限。
- 难度提高优先增加组合和判断，最后再增加数量。
- 实机可读性由人工测试决定，调度预算只提供工程约束。

## 12. 关卡一：群体割草

### 12.1 地图与节点

`L_Level01_Gate`：

1. 山门外：挥砍教学。
2. 山门内：远近敌人组合。
3. 演武场：清群与范围震荡。
4. 丹道入口：执事与支援。

每个节点配置 WaveDefinition、刷新区域、攻击预算、完成条件与下一节点。

### 12.2 开发顺序

1. 一块平地＋两个敌人验证近战。
2. 六个敌人验证申请攻击名额与横扫。
3. 加入一个远程敌人验证攻击组合。
4. 加入灵气收取与一次升级。
5. 连通两个节点并验证转场清理。
6. 扩充四段、替换场景资产、调至约 7 分钟。

波次使用有限敌人列表或有界生成规则。关卡控制器需要区分“当前场上无敌人”和“本波全部生成且全部处理”，避免过早结束。

### 12.3 验收

- 可以清楚感知群体战斗和一刀击败杂兵。
- 静止举盾仍需要调整朝向与恢复资源。
- 远程提示不会被近战特效持续覆盖。
- 所有节点可正常结束与推进。
- 未加载资产、失效生成点或敌人导航失败有诊断结果。

## 13. 关卡二：守点解救

### 13.1 目标状态

`ANLRitualObjective`：

- Integrity：法阵完整度。
- RescueProgress：解救进度。
- InterferenceSources：当前有效干扰来源集合。
- IsRescueCompleted：一次性的完成状态。

解救进度以战斗时间增加，基础有效守点约 240 秒。前后叙事与进入／离开使关卡总时长约 6 分钟。

### 13.2 干扰机制

每名破阵修士登记一个来源 ID。击杀、打断或离场时移除。

暂停、波次结束、恢复检查点时统一重建／清理集合，避免“敌人已死但进度继续暂停”的残留状态。

状态优先级：

1. 失败已锁定。
2. 完成已锁定。
3. 暂停。
4. 有效干扰。
5. 正常增加进度。

进度达 100% 后锁定成功候选，停止生成后续波次，处理规定的剩余有效威胁，再进入挚友获救事件。完整度归零与完成同帧时采用预先定义的结算顺序并测试，不能随蓝图 Tick 顺序变化。

### 13.3 波次

建阵 → 截阵 → 围攻 → 解封。

数据配置敌人的主要目标与允许攻击类型。攻击玩家与攻击法阵使用不同预警标识，但共用接触和伤害管线。

### 13.4 验收

- 双手不必长期按住交互。
- 法阵受击与玩家受击容易区分。
- 干扰来源死亡后进度恢复。
- 目标不要求玩家转身保护背后。
- 失败／重试／完成不残留生成器和干扰状态。
- 当前阶段检查点可恢复到可继续的资源状态。

## 14. 关卡三：Boss 与弹幕系统

### 14.1 Boss 状态

~~~text
Intro → PatternActive → GuardBroken → Vulnerable
      → Recover → PatternActive
~~~

另有 PhaseTransition、Defeated、Paused、Restoring。

生命建议先用 1500，三个阶段各约 500；这只是调试起点，最终以约 6–8 分钟的可读战斗为目标。护阵存在时可以被普通刃气逐步削弱，精准反弹更高效；护阵破裂后出现约 5 秒输出窗口。

生命、阶段、护阵、技能取消和结尾使用明确状态。不能根据累计播放时间直接宣布 Boss 死亡。

### 14.2 弹幕数据

BossPatternDefinition 包含：

~~~text
PatternId
PhaseId
DurationSeconds
TelegraphSeconds
Groups[]
  SpawnTimeSeconds
  SpawnOriginReference
  Count
  AngleStartDegrees
  AngleStepDegrees
  SpeedCmPerSec
  ProjectileDefinitionId
  TargetSamplingMode
  DamageEnabled
InterruptTargets[]
VulnerableWindowSeconds
RecoverySeconds
~~~

角度与空间参考以固定战斗节点为基准，不随玩家每次转头旋转整个弹幕阵列。

目标位置在预警／发射时按规定取样。首版飞剑使用可预测轨迹，不在无提示时持续追踪头部。

### 14.3 技能实现顺序

1. 单枚飞剑：发射、格挡、反弹、护阵扣减。
2. 飞剑连射：分组、节拍和恢复间隙。
3. 符弹扇面：形状识别、有限覆盖与空隙。
4. 丹火阵眼：蓄力、阵眼受击、取消技能。
5. 破阵输出：护阵崩解、弱点有效伤害。
6. 三阶段编排：重用前述规则、增加组合。
7. 结尾与挚友逃离。

第三阶段重组已教学机制，不通过突然出现的新判定制造难度。

### 14.4 阵眼与打断

- 阵眼有独立稳定 ID、生命、持续时间和攻击标识。
- 创建阵眼与开始蓄力使用同一技能实例。
- 阵眼击破只取消对应技能。
- 技能取消后清理待发射弹组、预警、计时器与目标引用。
- Boss 死亡／转阶段／重试必须取消旧技能。
- 打断失败造成一次有上限的明确伤害，不要求大招可用。

### 14.5 弹丸数量与表现

原型先以 32 枚同时有效弹丸作为压力测试档，再测试 64 枚。该数量是测试输入，不是性能承诺，也不是必须全部飞向玩家。

装饰飞剑可由 Niagara 承担，但：

- 有伤害的弹丸始终有对应可见表现。
- 装饰弹丸不产生伤害。
- 攻击形状、警告和实际规则一致。
- 弹幕视觉密集不等于同一时刻强制格挡密集。

调度器检查攻击到达时间与防御覆盖，人工检查是否存在不可读组合。第一版只验证本项目的有限技能组合。

### 14.6 验收

- 仅用基础刃气也能推进护阵与 Boss 战。
- 精准反弹带来可观察的效率提升。
- 阵眼击破可靠取消对应强攻。
- 暂停／恢复不瞬间释放积压的全部弹组。
- 阶段切换不残留旧技能与旧弹丸。
- 玩家无需大幅室内位移即可完成普通难度。

## 15. 成长、检查点与存档

### 15.1 成长

灵气自动吸收，首版两个升级节点：

- 一级 → 二级：第一关中后段／结束。
- 二级 → 三级：第二关中后段／结束。

建议先用 40／100 的累计灵气阈值调试；第一关结束提供二级保底，第二关结束提供三级保底。升级效果定义在 UpgradeDefinition，避免不同模块重复写伤害倍率。

一次敌人击败事件只奖励一次。统计与奖励使用有效事件 ID，不能在死亡动画、Actor 销毁、波次清理时分别奖励。

### 15.2 检查点快照


Boss 按阶段入口重试；守点按阶段入口重试；第一关按指定战斗节点重试。

### 15.3 恢复流程

1. 锁定战斗输入与关卡更新。
2. 停止波次、Boss 技能、导航请求和攻击调度。
3. 回收敌人、弹丸与临时特效，清理计时器。
4. 恢复局内成长与目标状态。
5. 根据稳定节点 ID 放置虚拟根节点；头手保持实时追踪。
6. 重建波次／阶段与随机状态。
7. 清空刀刃历史、伤害去重和输入残留。
8. 恢复到规定资源状态，显示准备提示。
9. 重新开放战斗。

保存采用临时文件写入后替换，并保留最近可用备份；读档需检查版本和关键配置 ID。具体文件写入实现通过本机平台验证。

### 15.4 随机性边界

相同随机状态保证阵容抽取与波次顺序可复现，不承诺物理、导航和用户动作逐帧一致。

死亡重试回滚到快照中的成长，不能保留失败段落的额外击杀灵气，从而避免反复重试刷等级。

### 15.5 测试

- 重试 10 次，敌人与弹丸数量不累积。
- 重试不增加灵气与爆发能量。
- Boss 阶段、法阵完整度、干扰来源与升级正确恢复。
- 失效资产 ID 有可诊断的失败或回退。
- 保存中断不会破坏最近有效快照。

## 16. 反馈、UI 与内容生产

### 16.1 反馈事件

以 CombatResult 的 FeedbackTag 选择音效、震动和 Niagara。

区分至少五种结果：普通命中、普通格挡、精准格挡、护势破防、法阵受损。

伤害逻辑先成立，再增加表现；特效不决定判定大小。

### 16.2 UI

采用事件驱动：

- 玩家生命与护势：腕部／法宝上的稳定状态。
- 解救进度与完整度：不同形状、独立数值。
- 爆发就绪：武器纹路与短提示。
- Boss 生命与护阵：前方世界内简洁状态。
- 移动方向与节点目标：短提示，避免长期遮挡。
- 开发 HUD：种子、攻击名额、挥砍状态、最近结果，仅开发构建显示。

正式游戏流程不显示源码类名、内部 ID 或工具连接状态。

~~~json

~~~

- RequestId 用于操作去重。
- 相同 RequestId、相同参数返回原结果。
- 相同 RequestId、不同参数返回冲突。

- dryRun 返回拟修改对象与验证结果，适用于资产修改工具。

~~~json

  "status": "completed",
  "changedAssets": [],
~~~

允许的状态包含 completed、failed、queued、running。长操作返回 OperationId，由后续查询取得结果；启动成功不能报告为任务已通过。

### 17.4 蓝图生产策略

AI 优先创建或更新薄蓝图子类、默认值和组件配置。复杂逻辑继续在 C++。

- 已编译父类。
- 所需组件与属性清单。
- 编辑器生成脚本或可执行项目工具。
- 人工补充步骤和验证方式。

## 18. 构建与测试入口

### 18.1 M0 构建环境

记录 UE 完整版本、安装路径、编译器、Windows SDK、项目路径和选定 Runtime。

截至核查，Epic 的 UE5.8 表列支持 VS2022 17.14+、VS2026 18.0+，一般开发推荐 VS2026。实际锁定组合先通过空项目 C++ 编译验证，再写入项目记录。[Visual Studio 官方配置说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/setting-up-visual-studio-development-environment-for-cplusplus-projects-in-unreal-engine)

使用 UBT 实际日志和退出码判断编译结果。

### 18.2 命令模板

以下命令是执行模板，项目名、路径与测试集合需在 M0／相关任务中填实。当前未在 UE 工程执行。

~~~powershell
$nlEngineRoot = '<UE5.8安装目录>'
$nlProjectFile = '<项目绝对路径>\Nilin.uproject'
~~~

测试启动参数建议由 Scripts/Build/RunTests.ps1 统一封装。该脚本需：

- 验证工具与工程存在。
- 传入实际测试集合。
- 设置报告输出目录与超时。
- 等待测试结束并读取报告。
- 识别失败、未运行及超时。
- 保留原日志，退出时给出正确失败状态。

Epic 支持通过命令行运行测试并导出 JSON／HTML 报告。具体启动和退出行为应在本项目的一组通过与一组故意失败的测试中验证。[运行自动化测试官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/run-automation-tests-in-unreal-engine)

带 NullRHI 的无图形测试只用于适合的规则；需要地图、渲染、XR 或设备输入的测试使用对应环境。

### 18.3 自动化层级

| 层级 | 内容 | 证据 |
|---|---|---|
| 编译 | C++、UHT 与模块依赖 | 完整日志、退出码 |
| 规则自动化 | 去重、资源、状态、奖励、恢复 | 测试报告 |
| 场景功能测试 | 生成、格挡链路、波次、目标、Boss | Functional Test 结果 |
| 内容验证 | 数据 ID、引用、蓝图、地图 Cook | 资产验证报告 |
| 桌面可运行 | 输入模拟、调试地图、流程 | 录屏／日志 |
| VR 实机 | 追踪、手感、舒适、性能 | 设备记录、人工表 |
| 打包验收 | 从干净目录启动完整构建 | 构建号、测试记录 |

UE 的 Automation 与 Functional Testing 可分别承担规则和关卡验证。[Automation Test Framework 官方说明](https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-test-framework-in-unreal-engine)

### 18.4 优先自动化的真实故障

1. 同一挥砍重复伤害。
2. 屏障格挡后身体仍受伤。
3. 精准窗口可通过快速按键无限重开。
4. 暂停仍消耗护势／增加进度。
5. 敌人死亡后攻击名额未释放。
6. 破阵修士死亡后干扰未移除。
7. 反弹弹丸保留敌方阵营。
8. 对象池复用保留旧攻击 ID。
9. 重试增加灵气。
10. Boss 技能取消后仍发出旧弹组。
11. 波次尚未生成完却判定完成。
12. 通关与失败同帧出现矛盾结果。

测试优先保护关键规则和已发现问题，避免为简单字段转发堆砌镜像测试。

### 18.5 打包流程

1. 从记录的可运行提交开始，完成完整编译和内容验证。
2. 明确启动地图、三张关卡地图及必要过渡地图，检查默认 GameMode 与 Pawn。
3. 检查软引用数据、Boss 弹幕资产和反馈资源的 Cook 包含规则。
4. 先生成 Windows Development 构建，验证日志、控制器输入和完整流程。
5. 再验证交付配置：隐藏开发 HUD，关闭开发连接与编辑器工具依赖。
6. 将构建输出到版本化目录，附引擎版本、提交号、内容版本和设备说明。
7. 从独立目录启动，检查存档可写、冷启动、退出重进和三关重试。

构建脚本调用本机 UE 自带构建／打包工具，具体参数在 ENV-01 的验证后锁定；成功创建输出目录不能代替打包日志与启动验收。

## 19. 性能方案

### 19.1 帧预算

| 刷新率 | 单帧理论预算 |
|---|---:|
| 72 Hz | 13.89 ms |
| 80 Hz | 12.50 ms |
| 90 Hz | 11.11 ms |
| 120 Hz | 8.33 ms |

若采用 90 Hz，原型可将应用 CPU 和 GPU 的稳定帧时间各以约 10 ms 以内为设计目标，留出余量；正式门槛以目标 Runtime 的测量定义为准。

CPU 与 GPU 的时间不能简单相加当作一帧总时间。记录 Game、Render、GPU 及 Runtime 结果，并判断真正瓶颈。

### 19.2 数量预算

| 项目 | 起点 | 扩大条件 |
|---|---:|---|
| 活跃战斗敌人 | 12 | 调度、可读性、CPU 全部通过 |
| 同时有效弹丸 | 32 | 再测 64 档压力 |
| 近战攻击名额 | 2 | 保持命中时间错开 |
| 普通远程名额 | 1 | 不覆盖关键近战预警 |
| 高威胁施法 | 1 | 组合可处理 |
| 骨骼与特效 | 先建立逐类成本 | 以实测决定远距简化和限额 |

人数、弹丸和特效分别有配置上限。超过上限时使用有序延迟、回收或降低装饰量，不静默删除玩家正在识别的关键攻击。

### 19.3 优化顺序

1. 测量，不先根据 AI 推测改渲染路线。
2. 调整攻击调度与 AI 更新频率。
3. 减少远距完整骨骼更新、复杂碰撞。
4. 对高频弹丸和短效反馈池化。
5. 控制透明屏障面积与粒子过绘。
6. 减少动态阴影和高成本材质。
7. 预加载关卡关键资源，避免战斗中同步加载。
8. 记录增量效果后再考虑更复杂框架。

近处关键敌人与手部判定不能因为优化而降低到明显延迟。

### 19.4 测量场景

- 第一关最大群体战斗，连续 5 分钟。
- 第二关最后守点波次，法阵与多种特效同时运行。
- Boss 第三阶段峰值弹幕，连续多轮。
- 连续重试 10 次，检查 Actor、内存、计时器与池计数。
- 打包版冷启动和首次进入各关。

报告记录构建号、电脑配置、头显、Runtime、刷新率、渲染分辨率、图形档位、测试种子。加载阶段和有效战斗区间分开统计。

## 20. AI 协作流程

### 20.1 一项任务的最小闭环

需求与依赖确认 → 实现 → 编译 → 场景配置 → 相关测试 → 实机待验项 → 更新文档与交付记录。

AI 每次处理一个可以明确验证的任务。跨模块接口变化同步更新依赖与契约，不把不兼容修改藏在表现调整里。

### 20.2 上下文包

每次任务提供：

1. 本方案对应章节。
2. 本任务卡。
3. 已锁定引擎、插件和工具能力。
4. 相关接口与当前源码。
5. 测试场景、稳定 ID 和预期行为。
6. 前一任务的实际交付记录。

无需每次把所有图像生成提示词、完整对话与无关源码塞进上下文。

### 20.3 AI 交付格式

~~~text
TaskId:
目标与最终行为:
修改文件与资产:
接口／数据变化:
实际执行的编译:
实际执行的测试:
日志与报告:
未验证的设备项:
已知问题与下一项依赖:
回滚范围:
~~~

未执行的步骤明确标为未验证。截图可以证明场景存在，不能证明高速格挡可靠或头显舒适。

### 20.4 接续记录

`Docs/AI/State.md` 始终记录：

- 当前里程碑与最近可运行提交。
- 正在处理的 TaskId。
- 已完成依赖。
- 当前地图与调试入口。
- 真实失败日志。
- 下一步具体操作。
- 等待实机验收的项目。

AI 会话中断或上下文压缩后，从这份记录接续，避免重复生成资产和重新搭建已完成系统。

### 20.5 资产协作

同一地图、同一蓝图或同一数据资产由一个当前任务负责写入。多人可以分工不同源码或独立资产，但合入前需统一内容引用与测试。

AI 对内容资产的写入串行执行，源码编译期间不继续修改对应反射声明或重建关联资产。

## 22. AI 提示词与任务模板

完整模板见 [AI 执行与任务模板](./AI执行与任务模板.md)。

推荐启动顺序：

1. ENV-01：创建或检查工程、完成真实编译。
2. AI-01：确认官方 MCP 接通并取得能力清单。
3. VR-01：真实设备与桌面调试输入。
4. CORE-01／02：共同契约与资源。
5. COMBAT-01 → 04：挥砍、弹丸、格挡、精准反弹。
6. ENEMY-01／DIR-01：一个近战敌人和调度。
7. SAVE-01／MOVE-01：重试与节点推进。
8. 验收短切片后进入三关。

首个可玩目标：玩家在固定点，用刀击败两个杂兵，用镜子挡下飞剑，成功反弹一次，并能无残留地重试该场景。

## 23. 里程碑与排期假设

估算前提：2 名能处理 UE C++／蓝图的开发者、1 名美术、策划／测试支持，使用现成基础资产并由 AI 辅助。按主要玩法链顺序估计约 41–60 个工作日，即约 8–12 周；这不是已承诺的工期。

| 里程碑 | 内容 | 估算工作日 | 阶段验收 |
|---|---|---:|---|
| M0 | 工程、工具链、MCP、硬件基准 | 2–3 | 可编译＋可连接＋实机输入 |
| M1 | Pawn、输入、暂停、节点移动 | 4–6 | 身体追踪与移动可靠 |
| M2 | 近战、弹丸、格挡、反弹、技能 | 6–9 | Combat Lab 完整闭环 |
| M3 | 敌人、调度、波次、第一关切片 | 5–7 | 割草体验成立 |
| M4 | 法阵、干扰、第二关 | 4–6 | 守点规则成立 |
| M5 | Boss 弹幕、阵眼、弱点、阶段 | 6–9 | Boss 规则可读、可完成 |
| M6 | 三关联通、成长、存档、UI、叙事 | 7–10 | 首次通关时长达标 |
| M7 | 表现、性能、舒适、打包与回归 | 7–10 | 交付标准满足 |

基础美术可与玩法并行，正式特效在判定和尺度稳定后替换。新资产量、头显数量、人员熟练度和已有代码会显著影响工期。

每阶段先修复未通过的关键验收项，再扩大内容。AI 生成速度不能直接等同于完整开发速度。

## 24. 风险与应对

| 实际关注点 | 发现方式 | 对应行动 |
|---|---|---|
| 自动移动不适 | M1 头显测试 | 默认淡出节点转移；连续推进独立验证 |
| 挥砍漏判／误判 | 轨迹可视化、不同速度动作 | 调整扫掠与识别，分离根节点运动 |
| 盾后仍受伤 | 同帧屏障／身体测试 | 统一接触顺序与结算 |
| 持续举盾无判断 | 完整战斗测试 | 调整护势、方向和恢复间隙 |
| Boss 弹幕无法理解 | 新手观察与失败原因 | 减少叠加，增加形状和节拍 |
| 检查点残留对象 | 连续重试 | 统一取消、回收和状态重建 |
| AI 引用不存在 API | 本机头文件与实际编译 | 修正 API，更新能力和版本记录 |
| MCP 能力缺失／变化 | 能力清单与失败记录 | 使用源码／编辑器正常入口，按需封装 |
| 二进制资产冲突 | 内容变更清单 | 单资产写入责任和提交协调 |
| 群体／透明特效超预算 | 峰值 Profiler | 限额、LOD、更新频率与特效优化 |

这些关注点直接对应当前游戏的实现任务与验收，以实际诊断确定处理。

## 25. 游戏内大模型的后续扩展边界

如后续明确要加入 AI 对话，可把挚友的非关键对话作为独立试验。

建议接口：NPC ID＋剧情阶段＋可用事实 → 候选台词＋受控表现指令。游戏逻辑验证阶段和指令，再决定是否播放；网络延迟或失败使用本地台词。

命中、格挡、弹幕节拍、目标生命与关卡胜负继续使用可测试的运行时规则。新增对话能力有独立里程碑，不改变当前三关的核心交付路径。

当前计划无需玩家联网或接入大模型服务即可完成整个游戏流程。

## 27. 实施建议

第一轮只做 Combat Lab：两个杂兵、一枚飞剑、一面盾、一次反弹、一处检查点。把 VR 操作可靠性与 AI 交付闭环同时打通。

通过后，以同一核心规则逐步搭建第一关、守点和 Boss。优先扩大被验证过的玩法，再增加美术复杂度和内容数量。
